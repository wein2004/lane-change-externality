# 專案逐段導讀（中文）

寫給要在評審面前為這份分析辯護的人。每一節先講「這一步在幹嘛」，再講「為什麼參數是這個值」。

讀完你應該能回答：**這個數字是怎麼來的，以及為什麼它不是假的。**

## 0. 一句話版本

> 我們量測「一次變換車道，讓後方那台車付出多少速度代價」，
> 方法是把每一次換道事件，跟**沒有發生換道、但條件相同的時刻**做對照。
> 結論是：代價真實存在（+0.76 km/h），但**它取決於當下路況，不取決於車種**。

如果只能講 60 秒，講這三句 + 為什麼需要對照組（見 §4）。

## 1. 資料：NGSIM 是什麼

美國聯邦公路總署（FHWA）在 2005 年用架高攝影機拍攝真實高速公路車流，逐格判讀每一台車的位置，產出 **10 Hz（每秒 10 筆）的車輛軌跡**。

我們用兩個高速公路路段：

| 路段 | 地點 | 原始筆數 | 路段長度 |
|---|---|---|---|
| I-80 | Emeryville, 加州 | 4,566,387 | 約 500 m |
| US-101 | 洛杉磯 | 4,802,933（去重後 4,098,933） | 約 640 m |

**為什麼不用另外兩個路段（Lankershim、Peachtree）？**
那兩個是有紅綠燈的市區道路。後車減速通常是因為紅燈，不是因為前面有人切進來。放進來會把「號誌造成的停等」算成「換道造成的代價」。

### 關鍵欄位

| 欄位 | 意思 | 單位 |
|---|---|---|
| `vehicle_id` | 車輛編號 | — |
| `frame_id` | 影格編號 | 1 格 = 0.1 秒 |
| `lane_id` | 車道編號 | — |
| `v_vel` | 速度 | **英尺/秒** |
| `space_headway` | 與前車的距離 | **英尺** |
| `following` | 正後方那台車的 ID | — |
| `v_class` | 車種：1 機車、2 小客車、**3 貨車** | — |

`v_class` 是整個專案的物流切入點：**3 號就是貨車，也就是物流車輛。**

`following` 是 NGSIM 自己算好的，直接告訴我們「誰在後面」——省掉自己推導車輛跟車關係的一整段工作。

單位換算只在 `src/ngsim.py` 做一次：1 ft/s = 1.09728 km/h。

## 2. `scripts/01_download_ngsim.py` — 下載

公開 API，不需要帳號。程式只抓需要的 12 個欄位、只抓兩個高速公路路段。

**為什麼用 `vehicle_id` 分段抓，而不是用 `$offset` 翻頁？**

第一版用 `$offset`。在 1,180 萬列的表上，翻得越深越慢，跑了 18 分鐘連一個檔案都沒產出。改成 `WHERE vehicle_id >= lo AND vehicle_id < hi`（資料庫有索引），實測 **81 萬列只要 49 秒**，而且從頭到尾速度穩定。

程式會**檢查每次請求有沒有撞到列數上限**。因為 Socrata 撞到 `$limit` 時是**安靜地截斷**，不會報錯——那會讓整批車輛憑空消失，而輸出看起來完全正常。

> 📌 被問到「你怎麼確定資料抓完整？」
> 答：程式比對 API 回報的總列數與實際抓到的列數，不一致會警告；且每次請求都檢查沒有觸及上限。

## 3. `src/ngsim.py` — 清理

這個檔案做三件事，每一件都擋掉一個會毀掉結論的錯誤。

### 3.1 去重

**US-101 有 704,000 列是逐位元完全重複的資料列**（佔 14.7%）。不是相似，是每個欄位都一模一樣。

因為完全相同，刪掉不損失任何資訊；但留著會讓那些車在每一個平均值、每一次 bootstrap 重抽、每一次配對裡被**算兩次**——而輸出不會有任何異狀。

### 3.2 切開錄影批次（最容易錯的一步）

每個路段其實是**三段 15 分鐘錄影接在一起**，而且 `vehicle_id` 和 `frame_id` 在每一段都**從頭開始編號**。

如果只用 `vehicle_id` 分組，兩段錄影裡編號相同的兩台不同的車會被接成一條軌跡——然後憑空生出一次「換道」。

**我們一開始用「時間間隔超過 60 秒就切」，這個做法錯了。**
I-80 的 17:00–17:15 和 17:15–17:30 兩段錄影在時間上是**連續的**，中間沒有間隔可切，結果兩段被合併，88 個車輛編號撞號。

**正確做法**：`frame_id` 也會重新編號，所以

```
epoch = global_time − frame_id × 100
```

在同一段錄影裡是**固定值**，不同段之間必然不同。兩個路段都剛好解出 **3 個 epoch**，對應 3 段錄影。

軌跡的唯一鍵是 `(路段, 錄影段, 車輛編號)`。

> 📌 被問到「你怎麼處理資料品質？」
> 這一段和 §3.1 就是答案。重點是：**這兩個問題在摘要統計上完全看不出來**，都是靠不相干的當機才浮出來。

### 3.3 速度平滑

NGSIM 的速度是由影像判讀出的位置**微分**而來，帶有大量高頻雜訊，這是文獻公認的問題（Punzo, Borzacchiello & Ciuffo, 2011, *Transportation Research Part C*）。

我們用 **11 格（1.1 秒）置中移動平均**平滑速度，並且**完全不用加速度欄位**（微分兩次，雜訊更嚴重）。

1.1 秒的理由：夠長，壓得掉微分雜訊；夠短，不會把真實的煞車反應抹平。

## 4. `scripts/02_detect_events.py` — 偵測事件 + 建對照組

**整個專案最重要的檔案。**

### 4.1 怎麼算一次「換道」

基本判準：同一台車的 `lane_id` 跟前一格不同。

然後兩道過濾：

| 過濾 | 門檻 | 擋掉什麼 |
|---|---|---|
| **穩定性** | 換道前後各要在同一車道待滿 **3 秒** | ①**偵測跳動**：只跳一格就回來，是判讀誤差不是動作 ②**連續蛇行**：4 秒內換 3 次被算成 3 個獨立事件 |
| **必須有後車** | `following` 不能是 0 | 沒有人承受代價，就沒有東西可量 |
| **只留主線車道** | I-80 車道 1–6、US-101 車道 1–5 | 匝道、加減速車道上的「換道」其實是**被迫匯入**，成因不同 |

**漏斗（實際數字）：**

```
I-80     原始換道 2,226 → 穩定性過濾 1,729 → 有後車 1,693 → 資料完整 1,484
US-101   原始換道 1,805 → 穩定性過濾 1,226 → 有後車 1,221 → 資料完整 1,047
                                                          合計 2,531 筆事件
```

扣掉機車後，分析用 **2,472 筆**（小客車 2,418、貨車 54）。

### 4.2 量什麼

以換道發生的那一刻為 `t = 0`：

| 視窗 | 範圍 | 用途 |
|---|---|---|
| 基準 | −4.0 秒 ～ −1.0 秒 | 後車「沒被干擾時」的速度 |
| 反應 | 0 ～ +5.0 秒 | 減速發生在這裡 |
| 恢復 | 0 ～ +10.0 秒 | 多久才回復 |

**為什麼基準在 −1 秒就停，不是停在 0？**
駕駛看到前車打方向燈常常**提前鬆油門**。如果把這段預期反應算進基準，基準會被拉低，效果會被低估。

輸出三個指標：

- `drop_kmh` = 基準速度 − 反應視窗內的最低速度
- `drop_pct` = 同上，但換算成基準的百分比（20 km/h 掉 5 跟 90 km/h 掉 5 不是同一回事）
- `recovery_s` = 從最低點回到基準 95% 所需時間，**上限截斷在 10 秒**

> ⚠️ **32.7% 的事件恢復時間是被截斷的**（路段太短，車還沒恢復就開出畫面了）。
> 所以我們報的恢復時間是**下界**，不是真值。這點要主動講，不要被問出來。

### 4.3 對照組 —— 這一步決定了結論算不算數

**問題：** 「換道後後車掉了 3.9 km/h」什麼都沒證明。塞車的車流本來就在不停地忽快忽慢，隨便挑一個時刻，車也常常在減速。

**做法：** 對「**沒有發生換道、但條件相同**」的時刻做完全一樣的量測。

候選條件：這台車在整個 −4 ～ +10 秒視窗內**都待在同一車道**，代表沒有人切到它前面。

然後用**最近鄰配對（nearest neighbour matching）、不重複取樣**，在「同路段 × 同壅塞程度」之內，依三個標準化後的變數配對：

| 配對變數 | 為什麼要它 |
|---|---|
| `baseline_kmh` | 它原本開多快 |
| `pre_trend_kmh` | **它原本是在加速還是減速** |
| `headway_pre_ft` | 它前方原本有多少空間 |

**三個都嚴格在 t = 0 之前量測。** 這裡有兩個踩過的坑，各自都改變了答案：

#### 坑一：只配速度會做出一個「不可能減速」的對照組（D8）

第一版只配速度水準。把對照組的原始速度曲線畫出來，發現它在視窗內**平均加速 23%**，而真實事件的後車是平的。

原因：在走走停停的車流裡，「條件在某個低速」會系統性地選到**剛從堵塞裡加速出來**的車——而一台正在加速的車，本來就不太可能再大幅減速。這個對照組**結構上就不可能呈現我們要量的效果**，會把效果高估。

加入 `pre_trend_kmh`（原本在加速還是減速）之後解決。

#### 坑二：配「換道當下的車距」是控制了結果（D10）

第二版用了 `headway_at_t`，也就是**換道那一刻**的車距。

這是 treatment 之後的變數。「被切入」的定義**就是車距突然變小**，所以配對它等於強迫每個對照組也承受同一個後果——把要量的機制配掉了。

影響有多大：

| 配對用的車距 | 結論 |
|---|---|
| `headway_at_t`（事後） | **−0.35 km/h**（CI −0.69 ～ −0.02）← 符號錯的 |
| `headway_pre_ft`（事前） | **+0.76 km/h**（CI +0.44 ～ +1.09）← 正確 |

**一個看起來完全合理的變數選擇，把結論的正負號翻了過來。**

> 📌 這是你們整份專案最值錢的一段。被問「你怎麼確定你的因果推論站得住？」時，講這個坑，比講任何方法名詞都有說服力。

### 4.4 我們怎麼「檢查」配對有沒有成功（而不是用嘴巴保證）

**檢查一：事前必須重疊。**
`fig1` 裡，對照組（綠）和事件組（藍）的平均速度曲線在 t = 0 之前**完全重疊**，之後才分開。這就是視覺化的「平行趨勢」證據。

**檢查二：用一個估計式根本沒看過的欄位驗證。**

| | 事前平均車距 | t=0 車距 | 變化 |
|---|---|---|---|
| 換道事件 | 106.3 ft | 63.7 ft | **−42.6 ft** |
| 配對對照組 | 105.8 ft | 102.7 ft | −3.2 ft |

事件組的後車在 t=0 掉了 42.6 英尺的車距，對照組只掉 3.2 英尺。

**這證明兩件事：**（1）我們抓到的真的是「切入」；（2）對照組真的沒被干擾。
而且 `headway_at_t` 這個欄位**沒有進入配對**，所以它是獨立的驗證，不是循環論證。

### 4.5 壅塞程度怎麼定義

每條車道切成 30 秒的格子，算格子內所有車的平均速度，低於 **25 km/h** 標為 `heavy`，以上標為 `light`。

**為什麼是 25 不是教科書的 40？**
NGSIM 兩個路段都是尖峰時段錄的，局部平均速度大約落在 5–47 km/h，中位數約 24。**用 40 切會讓 99% 的樣本都是「壅塞」，比較組直接變空的。** 切點是為了切開這份資料而選的，而且我們把它寫出來而不是藏著。

二分法只用在圖表呈現。**迴歸裡壅塞是連續變數。**

## 5. `scripts/03_analyse.py` — 統計

### 5.1 Bootstrap 信賴區間

每一個差異都報 **bootstrap 95% 信賴區間**（重抽 5,000 次，固定亂數種子 `20260919`），不報單一點估計。

原因：貨車只有 54 筆。點估計會暗示一個資料給不起的精確度。

### 5.2 迴歸：把「貨車效應」和「貨車都在哪裡換道」分開

原始的貨車 vs 小客車差異可能只是反映**貨車在什麼地方、什麼時候換道**（偏右車道、車流較慢、速度較低）。用 HC3 穩健標準誤的 OLS 控制住：

```
drop_kmh ~ is_truck + local_mean_kmh + is_truck:local_mean_kmh
           + baseline_kmh + space_headway + site
```

壅塞用**連續的局部平均速度**，不是二分虛擬變數——問題是「車流越慢，代價是不是越大」，二分法會丟掉大部分變異。

**實際結果：**

| 變數 | 係數 | p 值 | 怎麼讀 |
|---|---:|---:|---|
| `is_truck` | −1.364 | **0.468** | **控制之後，車種沒有統計顯著性** |
| `local_mean_kmh` | **−0.351** | **9e-67** | 周圍車流每慢 1 km/h，同一動作多讓後車掉 0.35 km/h |
| `baseline_kmh` | +0.470 | 1e-151 | 原本開越快，掉得越多（力學上合理） |
| `space_headway` | −0.035 | 3e-24 | 車距越大，受影響越小 |
| `site_c` | −3.241 | 3e-18 | US-101 整體影響小於 I-80 |
| `is_truck:local_mean_kmh` | +0.057 | 0.406 | 壅塞沒有特別放大貨車效應 |

**這張表就是整個結論。**

如果機制真的是「貨車又大又重所以干擾大」，`is_truck` 的係數應該撐得過控制變數。它沒有。撐過去的是 `local_mean_kmh`。

> **外部成本是「時機」的性質，不是「車種」的性質。**

## 7. `tests/test_detection.py` — 22 項檢驗

用**手工合成的軌跡**（答案是我們自己造的，所以已知）測核心邏輯：

- 一次乾淨換道 → 剛好偵測到 1 次，位置正確
- 單格跳動 → 被穩定性過濾擋掉
- 連續蛇行 → 被擋掉
- 注入固定的減速 → 量出來的數字對得上
- 不恢復的情況 → 正確標記為截斷
- 兩段錄影的相同車號 → 不會產生假換道
- **時間上連續的兩段錄影 → 仍然要被切開**（這條是 §3.2 那個 bug 的回歸測試）

跑法：

```bash
python tests/test_detection.py
```

> 答：核心偵測邏輯有 22 項合成資料檢驗，其中一項是為了我們實際踩過的 bug 補的回歸測試。

## 9. 誠實的限制（要主動講，不要被挖出來）

| 限制 | 怎麼講 |
|---|---|
| 貨車只有 54 筆 | 信賴區間已誠實反映。「這個結果值得注意是因為它**推翻了我們自己的假設**，不是因為它精確」 |
| 恢復時間 32.7% 被截斷 | 路段只有 500–640 m，報出來的是**下界** |
| 2005 年美國資料 | **方法可以移植，係數必須在本地資料重估**。這也正好是 Q2 服務的存在理由 |
| 觀察性研究 | 配對和迴歸移除了明顯的干擾因素，但這不是隨機試驗 |
| 單一後車、10 秒視窗 | 我們量的是**一階效果**。擾動會不會往後傳播成連鎖壅塞，這份資料的路段太短，答不了 |

最後一條特別重要，見 `docs/qa-prep.md` 的 Q9。
